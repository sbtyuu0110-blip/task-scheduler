## 1. 認める指摘① — 販路。ここは私が間違っていた

指摘のうち最も価値があるのは、7節の「実績ゼロなら待つより応募する方が有利」である。
これは正しく、しかも**HANDOFFの根本的な設計ミスを突いている。**

### 私が犯した誤り

HANDOFFの実行計画はこうなっていた。

```
ココナラに出品する → 3〜4週間待つ → 閲覧数が30貯まる → 判定する
```

**律速段階が「露出」になっている。そして露出はユーザーが制御できない。**

閲覧30に届かなければ「判定不能」であり、その場合の打ち手は
「タイトル・カテゴリ・タグを変えてまた3〜4週間待つ」しかない。
11月30日までに、この試行を何回できるか。**多くて2〜3回である。**

### さらに悪いことに、自分で集めた一次データが自分の計画を否定していた

HANDOFF §5に、私はこう書いている。

> ココナラ コンテンツマーケット — 46,122件／58.5%が¥500／**約74%が販売0件**

**74%が販売0件というデータを持ちながら、「出品して待つ」計画を立てていた。**
これは調査と意思決定が接続していない。指摘されて当然である。

### 応募型の何が構造的に優れているか

| | 出品型（ココナラ） | 応募型（クラウドワークス等） |
|---|---|---|
| 律速段階 | **露出**（制御不能） | **応募回数**（完全に制御可能） |
| 1回の試行コスト | 3〜4週間 | 数十分 |
| 11/30までの試行回数 | 2〜3回 | **数十〜百回以上** |
| 失敗時に分かること | 「露出が足りない」か「需要が無い」か**区別できない** | 提案文への反応が個別に返る |
| 相手の存在 | 未確認（誰かが見るかもしれない） | **確定**（発注者が実在し予算を出している） |

最後の行が決定的である。
出品型は「困っている人がいるはずだ」という仮説の上に立つ。
応募型は**すでに困って予算を出した人**のリストである。仮説を1段飛ばせる。

**したがって主軸を応募型に変更する。** これは指摘を受けた修正であり、私の判断の誤りである。

## 2. 認める指摘② — 「技術ではなく作業を売る」

21節の対照表（「GAS開発できます」ではなく「毎月の請求書作成を自動化します」）は正しい。
そして本日、ココナラの実リスティングを調べたところ**この指摘が裏付けられた。**

現在ココナラで上位に出てくる自動化系の出品は、こういう名前である。

- 「Excel VBAで作業自動化ツールを作成します **集計/転記/チェックリスト/データ整形/勤怠管理 etc…**」
- 「ExcelVBAによる自動化。**なんでも承ります** 集計転記/メール/印刷/PDF/シフト/大学数学/mac対応」
- 「自動化コンサル・お値段に合わせた仕組みを考えます **予算重視で自動化できることを考えます**」

**これは指摘が「やってはいけない」と言った売り方そのものである。**
「なんでも」「etc…」「お値段に合わせて」——買い手は自分の問題が解けるか判断できない。

一方、比較的新しいと見られる出品にはこういうものがある。

- 「**見積書作成を月50分→5分に**AIで自動化します AI×Excelで月10件分の見積書作成を一気に自動化」

1作業に限定し、削減時間を数字で示している。我々が設計した商品と**同じ型**である。

> ※ 新旧の推定はサービスIDの大小（420万番台 vs 100〜340万番台）からの推論であって、
> 掲載日を確認したものではない。ここは推論として扱う。

### 我々にとっての含意：市場は「逆方向」で埋まっている

検索結果に現れた出品を方向で分類すると、偏りがある。

| 方向 | 該当した出品 |
|---|---|
| **Excel → PDF**（帳票を出力する） | 一括変換ツール、顧客リストから一括PDF出力、請求書テンプレート作成 など**複数** |
| **PDF → Excel**（帳票を取り込む） | 「PDFや手書きの表から転記します」（**手作業の代行**・文字起こしカテゴリ） |

**PDFを"作る"側は混んでいて、PDFを"読む"側は薄い。**
そして薄い側に1件あるものは自動化ではなく手作業代行だった。

我々の商品はまさに「読む」側にある。これは有利な位置である。

> ※ これは検索結果に現れた範囲の観察であり、**全出品の網羅調査ではない。**
> 「競合が居ない」という主張はしない。「検索上位に同型が見当たらない」までである。

## 3. 認める指摘③ — ただし梯子はHANDOFFと矛盾しない

22節の「事務代行 → パターン発見 → 自動化 → 商品化」は妥当な経路である。
そして本日、**実際の発注データでこの経路が裏付けられた。**

クラウドワークスに、同じ「請求書PDF→Excel」という作業が、**2つの異なるカテゴリで**発注されている。

| 案件 | カテゴリ | 買い方 |
|---|---|---|
| 「【急募】PDF請求書からExcelへデータの転記をお願いいたします」 | **データ入力** | 人手でやってもらう |
| 「給与明細（CSV／PDF）から部門別・法定対応の賃金台帳へ自動転記する仕組み構築（Excel）」 | **エクセル作成** | 仕組みを作ってもらう |

**同じ痛みが、2つの買い方で市場に出ている。**
つまり「代行で入って自動化に転換する」は机上の梯子ではなく、
すでに両端が発注として実在している。指摘の経路は現実に対応している。

さらに、こういう案件がある。

- 「【スキマ時間業務/完全在宅】**請求書・領収書のデータ入力業務⑤**」

タイトル末尾の **⑤** は、同一発注者が同じ募集を繰り返していることを示唆する。
**反復する手作業＝自動化の転換先**として、これ以上に分かりやすい標的は少ない。

> ※ ⑤の解釈は推論である。連番の意味を発注者に確認したわけではない。

## 4. 却下① — レポートの内部矛盾。「売ってから作る」は応募型では成立しない

ここが、このレポートの最大の弱点である。

レポートは2つのことを同時に主張している。

1. （7節）実績ゼロなら**応募型が有利**である
2. （18節）**「売れなければ制作時間0時間」**——売ってから作れ

**この2つは両立しない。**

- **出品型**なら成立する。出品文を書くのは1時間。買われてから作る。制作リスクは確かに0。
- **応募型では成立しない。** 提案の時点で「この人は作れる」と発注者に判断させる必要がある。
  実績0・ポートフォリオ0の提案文は、レポート自身が引用した**応募125人**の中で選ばれない。

レポートは「応募125人→契約2人」という数字を挙げながら、
その競争を**何で勝ち抜くのか**を書いていない。「売ってから作る」では勝てない。

### したがって順序はこうなる

```
❌ 出品して待つ         （HANDOFFの誤り。露出が律速）
❌ 売ってから作る       （応募型では通用しない）
⭕ 先に1つ作る → 応募する → 並行して出品する
```

**先に動くものを1つ持つ。** それが応募型の入場券であり、出品型の信頼材料でもある。

そして、それは本日作った（§6）。

## 5. 却下② — 25候補への再拡張は、撤回済みの失敗の再演である

16節のスコア表を却下する。理由は「面倒だから」ではない。**方法論として同じ穴に落ちているから**である。

### 何が問題か

25候補 × 4指標 = **100個の数値**が提示されている。そのどれにも導出過程がない。
「Excel/GAS単機能自動化＝初顧客9点、AI議事録＝8点」——この1点差は何を根拠に付いたのか。

レポート自身が注記でこう書いている。

> ※この点数は「市場成功確率」ではありません。

**では何なのか。** 確率でないなら、この数値は何を意味し、どの判断を変えるのか。
答えは「何も変えない」である。実際、スコア表を経て出てきたTOP3は、
**Phase 2で4ラウンドかけて到達済みの結論と同じ**である。

### これはPhase 1で撤回した誤りと同型である

HANDOFF §4に、私が撤回した主張の記録がある。

> 「3ヶ月以内の初売上確率75〜85%」——**一次データなし。**

そして根本原因として、私はこう書いた。

> **市場規模と個人の初売上確率を混同していた**

25候補のスコア表は、この誤りを構造的に繰り返している。
「初顧客9点」は「市場にはこの手の案件がある」という観察を、
「あなたが取れる確率」に見える形式へ変換してしまっている。

**桁の揃った数値は、根拠の無さを隠す。** これはPhase 1の教訓そのものである。

### 個別案件の引用についても同じ問題がある

「応募125人→契約2人」「応募35人→契約0人」「応募10人→契約7人」——
これらは**1件ずつの事例（n=1）**であって、標本ではない。

レポートは「これは初心者の成功確率ではない」と正しく断っている。**その注意は妥当である。**
しかし断った上で、その数字を25候補のランキング根拠に使っている。**断りが機能していない。**

> なお本セッションでは **これらの数値を独立に検証できなかった。**
> crowdworks.jp は egress プロキシによりページ取得がブロックされており、
> 検索経由でタイトル・URLは取得できるが、応募数・契約数の欄は読めない。
> 「検証していない」とだけ記録する。誤りだと主張するものではない。

## 7. 修正後の実行計画

### 商品（変更なし）

**請求書PDF → Excel転記の自動化。テキスト層のあるPDFのみ。1発行元・1フォーマット。**

外部AIも独立に「面倒な作業を1個だけ消す」へ収束した。商品仮説は2系統から支持されている。
`research/phase2/05-execution-spec.md` の範囲を維持する。**スキャンPDF対応へは広げない。**

### 販路（ここを変更する）

| | 従来（HANDOFF） | 修正後 |
|---|---|---|
| 主軸 | ココナラ出品 | **クラウドワークス／ランサーズへの応募** |
| 従 | — | ココナラ出品（継続。ただし判定には使わない） |
| 律速 | 露出（制御不能） | **応募回数（制御可能）** |

### 判定基準（母数の定義を変更する）

HANDOFFは母数を「閲覧数」と定義した。**これを「応募数」に変更する。**
理由は§1のとおり、閲覧数はユーザーが制御できず、試行回数を稼げないため。

| 段階 | 指標 | 判定 |
|---|---|---|
| 試行 | 応募 **20件未満** | **判定不能。** まず件数を積む |
| 訴求 | 応募20件以上・返信 **0** | 提案文の問題。商品概念はまだ否定できない |
| 信頼 | 返信あり・受注 **0** | 実績不足か価格。返信の中身を読む |
| 成立 | 受注 **1以上** | 検証対象が「納品できるか」に移る |

ココナラの閲覧数基準（HANDOFF §3）は**そのまま残す**が、
これは従の指標であり、**閲覧が伸びないことを理由に商品を否定しない。**

### 中間判定（HANDOFF §3を差し替え）

| 時点 | 基準 | 満たない場合 |
|---|---|---|
| 9/30 | **応募20件到達**＋返信1件以上 | 提案文とターゲット案件の選び方を変える |
| 10/31 | 有料の初売上 | 価格と対象範囲を見直す |
| 11/30 | 累計3件＋反復パターンの発見 | 受託モデル自体を再検討 |

## 8. 本日やったこと — プロトタイプの完成

§4のとおり、応募型の入場券は「先に動くものを1つ持つ」ことである。
HANDOFF §8-A の「実装の下準備（テキストPDF抽出のプロトタイプ）」を実行した。

**`tools/invoice_to_excel/` に実装済み。ダミーデータで動作確認済み。**

### 実測で確認できたこと

| 確認項目 | 結果 |
|---|---|
| テキスト層PDFからの抽出 | **決定論的に成功。OCR不要**（Phase 2の前提が実証された） |
| 明細の検算（数量×単価=金額） | 動作 |
| 合計の突合（小計+税=合計） | 動作 |
| スキャンPDF（画像のみ）の検出 | **拒否した**。Excelには書かれない |
| 合計を改ざんしたPDF | **検算で停止**。`小計+消費税=23,430 だが 合計金額=234,300` |
| 二重計上の防止 | 転記済みの請求書番号を再転記しない |
| Excel出力の独立検算 | 明細総和133,500 = 小計総和133,500 ✓ |

### 開発中に検算機構が本物の欠陥を捕まえた

フォーマット定義の正規表現が `消費税(10%)` の **"10" を金額として拾っていた。**
検算が `小計+消費税=62,610 だが 合計金額=68,860` として停止し、
**誤った数字がExcelに入る前に止まった。**

これは実演として重要である。この商品が顧客に売っているのは
「転記する機能」ではなく**「間違いを顧客に届く前に止める機構」**であり、
それが開発中に自分自身のバグに対して発火した。

## 9. 次のアクション

### ユーザー（優先順）

1. **クラウドワークス／ランサーズに登録**し、次の語で案件を検索する
   `請求書 Excel 転記` / `PDF Excel 自動` / `データ入力 請求書` / `GAS 自動化`
2. **応募を20件積む。** 1件ずつの結果に意味を求めない。母数を作る
3. 提案文には**動くものがあることを書く**（プロトタイプの存在が差別化）
4. 並行してココナラに出品する（従。判定には使わない）

### 次セッションのAI

- **A. 応募20件未満** → 提案文の作成・改善。商品の是非を判断しない
- **B. 返信が来た** → 要件確認のヒアリング項目を作る。守秘・責任範囲を先に文書化
- **C. 受注した** → **最優先で納品支援。** 顧客フォーマット用の定義ファイルを作る
- **D. 応募20件・返信0** → 提案文とターゲット選定を変更。それでも0なら販路を再検討

### 禁止事項（HANDOFF §8を引き継ぎ、追加する）

- 新しい副業候補を提案し直さない（**5ラウンド**で決着済み）
- スキャンPDF対応への拡張を勧めない（責任問題）
- 一次データのない確率・スコアを提示しない（**候補のランキング表を作らない**）
- 「まず調査しましょう」で止めない
- **追加のプラットフォーム調査を新規に始めない。** 応募の実データが最優先
