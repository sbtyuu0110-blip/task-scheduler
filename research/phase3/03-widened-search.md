# 案件が見つからない問題の診断と修正

**作成日: 2026年8月28日**
**症状: 指示どおりに探しても、応募できる案件が出てこない**

---

## 1. 診断 — 絞りすぎた。私の指示の誤り

これまでに6つのフィルタを重ねて指示していた。

1. キーワードを「請求書」系に限定
2. 除外キーワード
3. 評価ゲート無し
4. テキストPDFのみ
5. 応募数が1桁〜20人台
6. タイトルに具体的な作業名がある

**1つずつは正しい。全部を同時にかけると、残る件数がほぼ0になる。**

### 母数がそもそも無かった

実測された件数（**募集終了を含む全期間の総数**）:

| 検索語 | 該当数 |
|---|---|
| `請求書 転記` | 31件 |
| `納品書 Excel` | 28件 |
| `請求書 Excel`（除外語あり） | 20件 |

現在募集中で範囲内のものは、この中の数件しかない。
**母数が数件しかないところで「応募20件を積む」と言っていた。** 計画として成立していなかった。

---

## 2. 根本原因 — 商品定義と探索範囲を混同していた

| | 内容 | 広さ |
|---|---|---|
| **商品**（顧客に売るもの） | 請求書PDF → Excel転記の自動化 | 狭くて良い。1顧客1作業 |
| **能力**（実際にできること） | **決まった形式のデータを読み、決まった表に、検算しながら入れる** | 広い |
| **探索範囲**（応募先を探す枠） | ← ここに**商品の狭さ**を持ち込んでいた | **誤り** |

顧客に売るときは狭くていい。「あなたのこの1つの作業を消します」でいい。
だが**応募先を探す段階で同じ狭さを使うと、母数が消える。**

### 広げても除外条件は1つも緩んでいない

`phase2/05-execution-spec.md` の対象外は、**リスクの定義**であってファイル種別の定義ではない。

| 対象外 | 状態 |
|---|---|
| スキャンPDF・写真・手書き | **維持**（OCRの検算責任） |
| 発行元ごとにレイアウトが異なるものの混在 | **維持** |
| 会計ソフトへの直接連携 | **維持** |
| 要件定義から／業務改善の提案 | **維持**（熟練度） |
| 長期常駐・週20時間以上 | **維持**（競争） |

**請求書PDF以外のデータ変換に広げても、上のどれにも触れない。**
これは商品の変更ではなく、**探索範囲の修正**である。

---

## 3. 修正後の探索 — 能力ベースの4群

除外キーワードは4語に統一する（`未経験` `初心者` は評価ゲート無しの信号なので外す）。

```
カンタン シンプル スキマ時間 主婦
```

検索URLの形式:
`https://crowdworks.jp/public/jobs/search?search[exclude_keywords]=<除外語>&search[keywords]=<検索語>`

### A群 — 帳票を読む（商品の中核）
`請求書 転記` / `PDF 転記` / `帳票 自動` / `納品書 取り込み`

### B群 — データを変換する（骨格が同じ）
`CSV 変換` / `CSV 整形` / `データ 整形` / `Excel 集約` / `ファイル 統合 Excel`

**入力がPDFかCSVかの違いだけで、「読む→検算→決まった表に書く」は同一。**
プロトタイプはフォーマット定義の差し替えで対応できる。

### C群 — 仕組みを作る（能力そのもの）
`転記 自動化` / `スプレッドシート 自動化` / `GAS 自動化` / `マクロ 作成` / `集計 自動化`

### D群 — 突合・照合（**検算が最大の強みになる**）
`突合 Excel` / `照合 自動` / `名寄せ` / `表記ゆれ 統一`

**D群は特に相性が良い。** 「合っているか確かめる」ことが依頼の本体であり、
我々のツールの中心機能（検算して合わなければ止める）がそのまま売り物になる。

---

## 4. 探し方の主従を逆にする

**薄いニッチではキーワード検索がすぐ枯れる。** 31件しかない語を毎日叩いても新しいものは出ない。

薄いニッチの正しい探し方は**カテゴリを新着順で毎日見ること**。
量はクエリの幅からではなく、**時間**から得る。

### 【2026/8/28 訂正】URLは渡さない。サイト内のナビゲーションから辿ること

当方は crowdworks.jp をegressプロキシで開けないため、**渡したURLを動作確認できていない。**
実際 `/public/jobs/special_features/14` はユーザー環境で開けなかった（特集ページは入れ替わる）。
さらに、前回渡したURLの一部は**発注者側URLからの推測**であり、実在を確認していなかった。

以下に区分を明示する。

#### 検索結果に実在が確認できたもの（jobs側）

| ページ | URL |
|---|---|
| Excel VBA・マクロ開発 | `/public/jobs/category/13` （`?page=2` でページ送り可） |
| Excel(VBA・マクロ) スキル | `/public/jobs/skill/423` |
| データ入力・集計(Excel) スキル | `/public/jobs/skill/12517` |
| AIシステム開発・導入・自動化支援 | `/public/jobs/category/370` |
| その他業務AI化支援 | `/public/jobs/category/372` |
| AI・チャットボット開発 | `/public/jobs/category/283` |
| キーワード検索 | `/public/jobs/search?search[keywords]=...` （**動作確認済み**） |

#### 未確認（推測で組み立てたもの・使わないこと）

`/public/jobs/skill/321`（GAS）／`/public/jobs/category/203`（エクセル作成）／
`/public/jobs/skill/9028`（データ集計・解析）／`/public/jobs/category/52`／`/public/jobs/category/149`

**これらは発注者側URL（`/public/employees/...`）から推測したもので、実在を確認していない。**

#### 確実な辿り方 — 左サイドバーを使う

URLを打つのではなく、画面のナビゲーションから入る。これなら番号が変わっても壊れない。

1. ヘッダーの **「仕事を探す」**
2. 左サイドバーの **仕事カテゴリ** から選ぶ

ユーザーのスクリーンショットで確認できたサイドバーの並びは以下。

> **AI-BPO（AI活用の業務改善）** ／ システム開発 ／ AI（人工知能）・機械学習 ／
> アプリ・スマートフォン開発 ／ ホームページ制作・Webデザイン ／ ECサイト・ネットショップ構築 ／
> デザイン ／ 動画・映像・アニメーション ／ …（略）… ／ 事務・カンタン作業

**先頭の「AI-BPO（AI活用の業務改善）」は未探索。名前がそのまま我々の領域なので最優先で開く。**

Excel系は **システム開発 → Excel VBA・マクロ開発** で辿れる。
スキル側のサイドバーには **アプリケーション（Windows Office/Adobe製品）** があり、ここにもExcelが入る。

#### 最も確実な運用 — 動く検索URLを1本持ち、キーワードだけ差し替える

キーワード検索URLは実際に動いた実績がある。これを基準にする。

```
https://crowdworks.jp/public/jobs/search?search[exclude_keywords]=カンタン シンプル スキマ時間 主婦&search[keywords]=<ここだけ変える>
```

検索結果ページの**左サイドバーにカテゴリの絞り込みがある**ので、
キーワードで引いてから結果ページ内でカテゴリを絞る方が、カテゴリURLを直接叩くより確実。

### 運用

1. 巡回中は判断しない。**気になったら「気になる！」ボタンで溜める**
2. 1日1回、溜めたものをまとめて開き、**応募条件を読む**
3. 評価ゲートがあれば飛ばす。無ければ応募する

**溜める作業と判断する作業を分ける。** 混ぜると、巡回のたびに迷って手が止まる。

## 5. ココナラ出品の位置づけを戻す

`phase3/00-response-to-rebuttal.md` で出品型を「従・判定には使わない」に降格した。
**判定に使わないという部分は維持する**（露出は制御できないため）。

だが「ほぼ無価値」であるかのように扱ったのは**行き過ぎだった。**

応募型にも供給側の制約があることが分かった以上、
**出品は一度書けば3ヶ月間ゼロコストで走り続ける経路**として並行させる価値がある。

| | 位置づけ |
|---|---|
| 応募型 | **主軸。** 判定の母数はこちらで数える |
| 出品型 | **並行。** 初期2時間で書いて放置。売れたら儲けもの。判定には使わない |

## 6. 現実的な母数の見積もり（正直に）

範囲内・ゲート無しの案件が **週1〜2件**の頻度で出ると仮定すると:

- 残り約94日 ≈ 13週
- 候補は **13〜26件**

**「11/30までに応募20件」は、広げた後でようやく届くかどうかの水準である。**
広げなければ届かない。これが今回の修正が必要だった理由。

なお、この頻度は推定であり実測ではない。
**巡回を2週間続けて、実際に何件出るかを数えること。** それが最初に取るべきデータになる。

---

## 7. 次にやること

1. **7日間、毎日カテゴリを巡回して「気になる！」に溜める**（判断しない）
2. 溜まったものの**応募条件を読み、ゲートの有無を記録する**
3. 7日後、次の3つを数える
   - 巡回で見つけた範囲内の案件数
   - うち評価ゲート無しの件数
   - 実際に応募できた件数
4. この3つが、9/30判定の実データになる

**1週間で0件だった場合は、クラウドワークス単独では母数が足りないという結論になる。**
そのときはランサーズを追加する。プラットフォームを増やす判断は、
「調べたいから」ではなく**「母数が足りないと実測されたから」**行う。
