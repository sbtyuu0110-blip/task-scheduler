# 請求書PDF → Excel 転記ツール（プロトタイプ）

`research/phase2/05-execution-spec.md` で確定した商品範囲を、実際に動くコードにしたもの。
**2026年8月26日、ダミーデータでの動作確認まで完了。**

---

## これは何をするか

同じ発行元・同じレイアウトの請求書PDFを読み、**検算に通ったものだけ**をExcelに追記する。

検算に通らなかったものは Excel に一切書かず、理由を表示して人間に返す。
「転記しないこと」がこのツールの主要な機能である。

## 対象と対象外（緩めないこと）

| | |
|---|---|
| **対象** | テキスト層を持つPDF（システムが発行した請求書）／1発行元・1レイアウト |
| **対象外** | スキャンPDF・写真・手書き／発行元ごとにレイアウトが違うものの混在／会計ソフト連携 |

スキャンPDFはOCRが必要で、AI-OCRの精度は公称99%だが**100%は理論上不可能**。
誤認識を誰が検算するのかという責任問題が発生するため、構造的に除外している。
このツールはテキスト層が無いPDFを検出して**拒否する**。

## 使い方

```bash
pip install pdfplumber openpyxl reportlab

# 検算だけ実行（Excelには書かない）
python3 invoice_to_excel.py 請求書/*.pdf \
  --format formats/sample_logistics.json \
  --excel 台帳.xlsx --dry-run

# 実際に追記する
python3 invoice_to_excel.py 請求書/*.pdf \
  --format formats/sample_logistics.json \
  --excel 台帳.xlsx
```

終了コードは、全件転記できたとき `0`、1件でも転記しなかったとき `1`。

## 4つの安全機構（実測で確認済み）

| 機構 | 動作 |
|---|---|
| **テキスト層の検出** | 抽出文字数が50字未満ならスキャン疑いとして拒否 |
| **明細の検算** | 各行の `数量 × 単価 = 金額` を照合 |
| **合計の突合** | `明細合計 = 小計` かつ `小計 + 消費税 = 合計金額` を照合 |
| **二重計上の防止** | 転記済みの請求書番号は再転記しない |

いずれかに失敗した請求書は Excel に**書かれない**。部分的な転記はしない。

### 実際に捕捉した例

開発中、フォーマット定義の正規表現が `消費税(10%)` の `10` を金額として拾っていた。
検算が `小計+消費税=62,610 だが 合計金額=68,860` として停止し、
**誤った数字が Excel に入る前に止まった。**

これは、このツールが顧客に対して保証している価値そのものである。

## 新しい発行元に対応する

`formats/sample_logistics.json` をコピーして正規表現を書き換える。
1ファイル = 1発行元。**1つの定義で複数レイアウトを扱おうとしないこと。**

```json
{
  "header":    { "invoice_no": "...", "issue_date": "...", "customer": "..." },
  "line_item": "^(?P<name>.+?)\\s+(?P<qty>[\\d,]+)\\s+(?P<unit>[\\d,]+)\\s+(?P<amount>[\\d,]+)$",
  "totals":    { "subtotal": "...", "tax": "...", "total": "..." }
}
```

金額を拾う正規表現は、上の実例のとおり**桁を取り違えやすい**。
新しい定義を作ったら必ず `--dry-run` で検算を通してから使う。

## 納品時に必ず伝えること

- 転記結果の**最終確認は発注者側**が行う（このツールは検算するが、正当性を保証しない）
- 受領した請求書PDFは作業完了後に削除する
- 取引先名・金額は第三者に開示しない
- 初回テストは顧客の実データではなく**ダミー**で行う
