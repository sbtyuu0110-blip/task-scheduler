# 引き継ぎ（セッション間コンテキスト引き継ぎ）

長い作業の途中でコンテキストが埋まると、次のセッションはゼロから始まる。引き継ぎ書の目的はただ一つ、**次のセッションが数分で作業を再開できること**。議事録ではない。「何をしたか」より「次に何をすればいいか」「なぜそう決めたか」が本体になる。

書く相手は、この会話を一度も見ていない別の Claude だと思って書く。「さっき話した件」「例のバグ」「前回の方針」は通じない。固有名詞・ファイルパス・コマンドで書く。

## 手順

### 1. まず、消える作業を消えないようにする

リモートセッション（Claude Code on the web）のコンテナは破棄される。**未コミット・未プッシュの変更は、引き継ぎ書に書いても復元できない。** だから引き継ぎ書より先に、作業の確定を済ませる。

```bash
git status --short --branch
git log --oneline @{u}..HEAD 2>/dev/null || echo "上流未設定: git push -u origin <branch> が必要"
```

上流が未設定のブランチでは `@{u}` が失敗する。エラーを握りつぶして「プッシュ漏れなし」と読み違えないこと。

- コミットできる状態の変更 → コミットしてプッシュ
- まだ壊れていて正式にコミットしたくない → `wip: <何が途中か>` でコミットしてプッシュ。次のセッションが続きから直せる。「あとで整える」WIP は、失われるよりはるかにいい
- ユーザーが明示的にコミットを止めている → `git diff` の全文を引き継ぎ書に貼る（それ以外に持ち越す手段がない）

迷う変更が残っているならユーザーに確認する。ここで失うと取り返しがつかないので、聞くコストの方が安い。

### 2. 事実を集める（記憶で書かない）

長い会話の記憶は圧縮されていて細部がずれる。憶測で書いた引き継ぎ書は、次のセッションを間違った方向に走らせる分だけ無いより有害になる。必ずコマンドで裏を取る。

```bash
git branch --show-current
git log --oneline -10
git status --short
ls .claude/handoff/ 2>/dev/null        # 前回の引き継ぎ書があるか
```

あわせて確認する：

- **PR** — 番号・状態・CI の結果・未対応のレビューコメント（GitHub MCP ツールがあれば実際に読む）
- **テスト / lint** — 落ちているものがあるなら、実際に走らせて出力をそのまま記録する。「たぶん直った」は書かない
- **未完のタスク** — TodoList、バックグラウンド実行中のジョブ、監視中の PR やスケジュール
- **未解決の質問** — ユーザーに投げたまま答えをもらっていない判断

### 3. 引き継ぎ書を書く

保存先は `.claude/handoff/YYYY-MM-DD-<短いスラッグ>.md`。`docs/` ではなく `.claude/` に置くのは、これがプロダクトのドキュメントではなくセッションの作業メモであり、公開サイトやビルド成果物に混ざらないため。ユーザーが別の場所を指定したらそれに従う。

このテンプレートを使う。埋まらない節は「なし」と書いて残す。節ごと消すと、次のセッションは「書き忘れ」か「本当に無い」かを判断できない。

```markdown
# 引き継ぎ: <一行で何の作業か>

- 日付: YYYY-MM-DD
- リポジトリ / ブランチ: <repo> / <branch>
- 前回の引き継ぎ書: <パス、なければ「なし」>

## 1. ゴール
ユーザーが最終的に何を得たいか。1〜3 行。個々のタスクではなく、完了条件を書く。

## 2. 現在地
どこまで終わっているか。完了したものと、動作確認まで済んだものを区別する。

## 3. 次にやること
優先順に、具体的な動詞で。「認証まわりを見る」ではなく
「src/auth.ts:42 のトークン期限チェックを UTC 基準に直し、npm test -- auth を通す」。
先頭の 1 件は、次のセッションが読んだ直後に着手できる粒度にする。

## 4. 作業中の状態
- ブランチ / 最新コミット:
- 未コミットの変更: あり / なし（あるなら内容と理由）
- PR: #番号 と状態、CI、未対応のレビュー
- 落ちているテスト: コマンドとエラーの実際の出力

## 5. 決めたことと、その理由
採用した方針と、なぜそれにしたか。理由がないと次のセッションが同じ検討をやり直すか、
良かれと思って勝手にひっくり返す。

## 6. 試して駄目だったこと
やって失敗したアプローチと、なぜ駄目だったか。同じ穴に落ちるのを防ぐ。
ここが引き継ぎ書でいちばん時間を節約する節になることが多い。

## 7. 関連ファイル
path/to/file.ts:120 — 何がそこにあるか、なぜ重要か（行番号まで書く）

## 8. ユーザーの好み・制約
この作業で判明した、指示されないと分からない前提。
（使う / 使わないライブラリ、命名、口調、コミットの粒度、触ってはいけない箇所 など）

## 9. 再開手順
そのまま実行できるコマンド列。
```

**読みやすさより正確さを優先する。** 各項目は、前提知識なしで読んで一意に解釈できるか確認する。

### 4. コミットしてプッシュする

引き継ぎ書自体がプッシュされていなければ、コンテナが消えた時点で一緒に消える。

```bash
git add .claude/handoff/<file>.md
git commit -m "docs: <作業名>の引き継ぎ書を追加"
git push -u origin <branch>
```

### 5. チャットに再開プロンプトを出す

本体はファイル側にあるので、ここは短く。次のセッションの最初に貼るだけで動き出せる形にする。

```
前回の続きです。<repo> の <branch> で作業しています。
まず .claude/handoff/<file>.md を読んでから再開してください。

ゴール: <1行>
次の一手: <1行>
```

そのあと 3〜5 行で、いま何が終わっていて何が残っているかを口頭で補足する。

## 次のセッション側での使い方

ユーザーが「引き継ぎ読んで」「前回の続き」と言ったとき：

```bash
ls -1 .claude/handoff/ | tail -3
```

いちばん新しいものを読み、「4. 作業中の状態」を `git status` / `git log` / PR の実際の状態と突き合わせる。引き継ぎ書は書かれた時点のスナップショットなので、その後に誰かが動かしている可能性がある。食い違いがあればユーザーに伝えてから進める。

## 書かないこと

- **会話のログ** — 引き継ぎ書は要約ではなく作業指示書。「ユーザーが〜と言った」の羅列は要らない
- **秘密情報** — トークン、API キー、パスワード、個人情報。リポジトリに commit される前提であることを忘れない
- **憶測** — 確認していないことを断定で書かない。不明なら「未確認」と書く
- **コードの丸写し** — ファイルパスと行番号で指せば済む。引き継ぎ書がコードの複製になると、すぐ古くなって嘘になる

## git リポジトリでない場合

ファイルとして残せないなら、チャットに引き継ぎ書の全文（上のテンプレートそのまま）を出し、ユーザーに保存を促す。この場合はファイルがない分、チャット出力が唯一の引き継ぎ経路になるので省略しない。
